# HMS-T-02: PostgreSQL schema and migrations

This is a standalone database component based on the supplied HMS Architecture and Design Specification (SAD), especially sections 3.6, 3.7 and 4.1, plus the T-02 backlog description. It is intended to be integrated into the main repository after T-01 establishes the project structure.

## Included

- PostgreSQL 15 via Docker Compose.
- Ordered SQL initialization files in `database/migrations/`.
- Tables for users, patients, patient history, doctors, appointments, visits, prescriptions, bills, bill items, payments and audit log.
- Foreign keys, check constraints, uniqueness constraints and indexes.
- Partial unique index preventing two `Confirmed` appointments for the same doctor and slot.
- Insert-only enforcement for `audit_log` rows.
- Development-only seed users for all five roles, a doctor and two sample patients.
- SQL verification script.

## Start the database

From this directory, with Docker Desktop/Docker Engine running:

```sh
docker compose up -d
```

Wait until it is healthy:

```sh
docker compose ps
```

Connection settings for local development:

- Host: `localhost`
- Port: `5432`
- Database: `hms`
- User: `hms_app`
- Password: `local_dev_only_change_me` by default (set `POSTGRES_PASSWORD` in `.env` to override)

Run the verification checks:

```sh
docker compose exec -T db psql -U hms_app -d hms < database/tests/verify.sql
```

Stop the database:

```sh
docker compose down
```

To delete the local database volume and start from a clean database (this permanently deletes local DB data):

```sh
docker compose down -v
docker compose up -d
```

## Important notes before integration

1. **Docker init scripts run only on an empty data volume.** If you edit a migration after first startup, reset the local volume or apply the new migration manually. For a shared/team environment, use a migration ledger/runner so already-applied migrations are tracked. The SQL files are versioned, but this initial standalone component does not yet include a C++/libpqxx migration runner because T-01's application scaffold is not in the supplied ZIP.
2. **Encryption is not implemented by SQL.** SAD specifies field-level AES-256 encryption in the data-access layer. The `BYTEA` columns for fields marked with `*` are intended to hold ciphertext; the seed values are labelled demo placeholders, not real AES ciphertext. Implement encryption/decryption in the C++ DAL using OpenSSL 3 and keep keys outside source control.
3. **Patient search versus encryption needs a DAL decision.** SAD 3.7 requests indexes on patient name and phone, while SAD 4.1 marks both encrypted. A normal B-tree index over randomized ciphertext will not enable plaintext name/phone search. The current indexes are present, but efficient privacy-preserving search requires a reviewed keyed blind-index design (e.g. keyed HMAC columns) or another explicitly approved design. Do not silently store plaintext or use deterministic encryption without a security review.
4. **Seed login credentials are intentionally disabled.** Seed `password_hash` values are sentinel strings, not valid Argon2id hashes. Replace them with hashes generated by the application before attempting login; no real passwords are included in this repo.
5. The SAD's short table overview does not specify every column or every enum value. The added columns/constraints here are implementation choices to support referential integrity and common workflows; review them with the team before merge.
6. PostgreSQL cannot make a table absolutely immutable against its owner/superuser. The trigger prevents ordinary row-level UPDATE/DELETE statements; production permissions should additionally grant the application role INSERT/SELECT only on `audit_log`.
7. The SQL migrations and verification script have been run successfully against a fresh local PostgreSQL 18 database (`hms_t02_test`). Docker Compose has not yet been tested; validate it separately if Docker is available before claiming the Compose setup was tested.
